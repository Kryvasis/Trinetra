# Trinetra

## 1. What this is, in one paragraph

**For the judge who has 30 seconds:** Trinetra is a tool that lets a network team check whether their routers and switches are set up securely — even when those devices come from different vendors and speak different configuration languages — by uploading the devices' text config files, automatically comparing them against four major security standards, flagging anything it doesn't understand so a human can teach it once, and then producing a tamper-proof report that tells you what passed, what failed, how bad each failure is, and exactly what to type to fix it.

**One-sentence version to repeat:** *"Trinetra is an AI-assisted, multi-vendor network config auditor that turns uploaded CLI configs into standards-mapped, tamper-evident compliance reports without needing to re-deploy code when a new vendor is added."*

---

## 2. The problem, explained simply

Today, checking whether a network is configured securely means a human reading hundreds of lines of cryptic, vendor-specific text — Cisco IOS looks nothing like Juniper JUNOS, and each version adds its own quirks — then manually matching each setting against long checklists from CIS, NIST, ISO, and STIG, one device at a time. That work is slow, error-prone, and locked to the few people who know each vendor's syntax; add a new vendor and you usually have to rewrite tooling. The result is inconsistent audits, missed misconfigurations, and reports that can't prove they weren't tampered with after the fact. Trinetra was built to make that process repeatable, vendor-agnostic, and auditable.

---

## 3. How it works, step by step

*No code, just the flow a stakeholder can follow:*

1. **Upload a config** — You pick a session name and drag in one config file or many at once (for example, `cisco-lab-01.txt`, `juniper-lab-01.txt`, `fortigate-lab-01.txt`, `panos-lab-01.txt`). You can also add the device's serial number, hardware model, and OS version if you have them; if you leave OS blank, the system reads it from the config header itself. **Config-file upload is the PS-recommended primary method.**

2. **Fetch from IP/URL (optional, additive)** — Alternatively, supply an IP/hostname (SSH) or URL (HTTP GET) and credentials; the system fetches the raw config text and feeds it into the *exact same* ingestion pipeline as a file upload — no second parsing path. This is an auto-sourced convenience (requires network reachability), not a replacement for offline upload, and not a live-scanning/fingerprinting system.

3. **System reads it** — The system figures out which vendor it is (`Cisco/Juniper/FortiOS/PAN-OS/Generic` `TrinetraConfigIngestor.java:82` + `VendorConnectorRegistry.java:22`), breaks the config into lines, and normalizes it into a vendor-neutral `SecurityBaseline` (`src/SecurityBaseline.java:1` `managementPlane/authentication/snmp/logging` with evidence lines). Known lines matched via `VendorTrainingMap` + `KNOWN_PATTERNS` per vendor; unknown lines flagged.

4. **Compare against security frameworks** — For every recognized setting, the baseline facts are evaluated (`src/SemanticControlEvaluator.java:1` for `V-003/006/013/057/058/071/107`, Cat2 remains `manual_review`) then mapped to the controls in the frameworks you selected — CIS, NIST 800-53, ISO 27001, and STIG. You can choose to score all four or just the ones you care about. Honest boundary: static config `V_code` verdicts remain `manual_review` (`Runtime evidence required` per `bridge/tests/test_config_upload_differentiation.py:100`), differentiation via `CFG-*` observations + baseline evidence; live probes (`trinetra -stat run`) remain the only `pass/fail` source — not a certification.

5. **Flag what it doesn't know** — Any line it has never seen before is listed as "unrecognized," grouped by device.

6. **A human teaches it** — In a simple form, you tell it what that new line means: which vendor it belongs to, what security category it is, which standard it maps to, and how to fix it if it's wrong. You can also note which OS version you saw it on.

7. **It remembers** — That teaching is saved as a pattern. The next time you upload the same kind of config, the line is recognized automatically — no code change, no redeploy.

8. **Produce a report with fixes** — For any failures, it shows a risk level (critical/high/medium/low) and a numbered, device-specific list of commands to type to fix it. The whole thing is packaged into a report where every result is hash-chained, so anyone can verify afterward that the evidence hasn't been altered. Fetch-sourced devices appear identically but tagged `ingestion_method: live_fetch` for honest reporting. **Per-device PDFs:** `GET /api/session/<name>/devices/<device_id>/pdf` gives a single PDF per device (`audit_report_<device>_<session>.md` + baseline JSON) — the PS-required `single PDF per device` — in addition to the session-combined PDF.

## 5. What makes this different (differentiators)

### 5.1 Tamper-evident hash chain

*Plain language:* Every test result is linked to the one before it like a chain — if someone later edits or deletes a result, the chain breaks and the report says so. That lets an auditor prove the evidence hasn't been tampered with after collection.

*Technical detail:* `src/TrinetraSession.java:400-620` maintains `normalized_results[]` where each entry stores `chain_hash = SHA-256(previous_chain_hash + canonical_json(entry_without_hash))`, seeded with `GENESIS_HASH = SHA-256("TRINETRA_GENESIS")`. `previous_chain_hash` is tracked separately and updated atomically inside `withSessionStateLock` (in-process `ReentrantLock` + cross-process `FileChannel.lock` on `<file>.lock` sidecar, `TrinetraSession.java:320-383`) so concurrent uploads don't fork the chain. `verifyChain()` recomputes each link; `TrinetraAuditReportBuilder.java:290` and PDF metadata embed `Chain Status: INTACT (N links)` or `BROKEN at index`. The same chain is mirrored in the append-only SQLite `trinetra_audit.db` (`TrinetraAudit.java:110`) via per-run `run_uuid`, linking audit rows to chain tip.

### 5.2 Deterministic scorer with AI narration

*Plain language:* The compliance percentage is calculated by plain arithmetic from a file that lists which test maps to which control — no AI involved, so the number is always reproducible. AI is only used afterward to turn those numbers into readable paragraphs, and even then the system checks that the AI didn't invent any numbers.

*Technical detail:* `src/TrinetraComplianceScorer.java:41` is pure data transformation: for each `normalized_results` entry, `TrinetraCompliance.getControlMappings(testId)` (`src/TrinetraCompliance.java:64`) yields `framework → [controlIds]`; an accumulator per framework counts `tests_passed/tests_failed/controls_covered`; `compliance_percentage = round(tests_passed*100/total)`. No LLM call. `src/TrinetraNarrativeGenerator.java:41` then calls Gemini CLI (`TrinetraCommon.execGemini`, Gemini 2.5 Flash-Lite) with `renderAllowedValues` and `collectExpectedNumbers`; `validateNarrative()` extracts every numeric token and requires it to be in the scorer's exact set and that every framework's percentage appears — otherwise it retries once then falls back to `buildTemplateBody()` and the report is labeled `TEMPLATE-GENERATED`. The narrative never writes to the chain.

### 5.3 No-redeploy training loop

*Plain language:* When the system sees a command it doesn't recognize, it shows it to you, you fill in what it means, and from then on it recognizes that pattern on any device — you never edit code or restart the system.

*Technical detail:* `src/VendorTrainingMap.java:20` stores `vendor + pattern (regex) + securityCategory + controlMapping + remediation + osVersion` in `config/vendor_training_map.json`. `TrinetraConfigIngestor.java:131-180` classifies each config line: first `findMatch(canonicalVendor, line)` (regex `Pattern.compile` + substring fallback) against training entries, then `KNOWN_PATTERNS` (`Cisco/Juniper/FortiOS/PAN-OS/Generic` `TrinetraConfigIngestor.java:18` now 4 vendors), otherwise mark `unrecognized`. Training entries are written by `bridge/app.py:681` `POST /train` via atomic `NamedTemporaryFile` + `os.replace`; `VendorTrainingMap.load()` checks `Files.getLastModifiedTime` to invalidate its `cache` without process restart (`VendorTrainingMap.java:38-49`). `TrinetraSession.setUnrecognizedLines()` and `GET /unrecognized` surface per-device unrecognized lines to `frontend/src/pages/TrainingView.jsx:48` for the click-to-select form.

### 5.4 Lightweight ML advisory (parallel, not authoritative)

*Plain language:* Alongside the exact regex check, a tiny machine-learning helper looks at unfamiliar lines and suggests what they might mean — like autocomplete for the training form. It never decides pass/fail on its own; a human still approves, and the compliance percentage never comes from ML.

*Technical detail:* `bridge/ml_knn.py:1` is `TfidfVectorizer(analyzer='char_wb', 3-5)` + `KNeighborsClassifier(k=3, metric='cosine', weights='distance')` (`sklearn` `bridge/requirements.txt:6`), corpus `config/ml_corpus.json` seeded from `src/TrinetraConfigIngestor.java:19` `KNOWN_PATTERNS` `32` entries plus `config/vendor_training_map.json` entries. `src/MlBridge.java:1` calls `python -c` `predict(line)` with `4s` timeout and `.venv/bin/python` fallback, gated `confidence>=0.55`. `src/TrinetraConfigIngestor.java:224` runs it **parallel** after regex: advisory `ml_advisory` attached to the `UNRECOGNIZED` finding and `POST /api/ml/suggest` `bridge/app.py:1120` surfaces `AI: V-006 100%` badges in `frontend/src/pages/TrainingView.jsx:276` — one click prefills the form. `POST /train` retrains `config/ml_model.pkl` `bridge/app.py:1105`. Scorer `src/TrinetraComplianceScorer.java:11` stays deterministic; ML findings are `V-XXX_ML` `manual_review` advisory, never in `normalized_results`.

### 5.5 Vendor-neutral baseline (new)

*Plain language:* Instead of checking each vendor's different wording directly, the system first translates every config — Cisco, Juniper, FortiGate, Palo Alto — into the same simple facts: "is telnet on?", "is SSH version 2?", "is SNMP public?", "is logging to a host?". The security checks then look at those facts, not the vendor syntax.

*Technical detail:* `src/SecurityBaseline.java:1` defines `managementPlane{sshEnabled/sshVersion/telnetEnabled/httpEnabled/execTimeout}`, `authentication{aaaEnabled/hasEnableSecret/users[{name,authType}] }`, `snmp{communities[]}`, `logging{enabled/hosts}` each with `evidenceLines` (`L15: ip ssh version 2`). Adapters `src/CiscoBaselineAdapter.java:1`, `JuniperBaselineAdapter.java:1`, `FortiGateBaselineAdapter.java:1`, `PaloAltoBaselineAdapter.java:1` parse `configContent` into `SecurityBaseline`; `src/SemanticControlEvaluator.java:1` maps `V-003/006/013/057/058/071/107` to `PASS/FAIL` from baseline (Cat2 remains `manual_review`). `TrinetraConfigIngestor.java:135` `buildBaseline(canonicalVendor,config)` stored per-device `TrinetraSession.java:1029` `device_baselines` (`sessions/<s>/<s>.json` `device_baselines` + `brain_state` evidence) and shown in per-device report `TrinetraAuditReportBuilder.java:341` `## Baseline (vendor-neutral)`. Honesty: `V_code` verdicts for config remain `manual_review` (`Runtime evidence required` per `bridge/tests/test_config_upload_differentiation.py:100`), baseline evidence is supplemental — live probes stay the only `pass/fail` source.

*Pitch:* **rule-driven scorer + lightweight supervised ML (TF-IDF + KNN) for unseen-syntax suggestion, human-approved — not LLM semantics.**

### Technical deep-dive answer (when a judge asks "how does the AI/training loop actually work?")

> "The compliance percentage is not from AI — it's deterministic: each test maps to controls in a JSON manifest, so `tests_passed/total` per framework is pure arithmetic. Training is pattern-based: you map an unrecognized line to a regex and a security category, it's stored in `vendor_training_map.json` and the ingestor's `findMatch` uses `Pattern.compile` against each line on the next upload — no Java redeploy, just an mtime cache check. **Alongside regex, a lightweight ML helper `bridge/ml_knn.py` (TF-IDF char 3-5 + KNN k=3 cosine, `src/MlBridge.java`) runs in parallel: it suggests a label with confidence for unrecognized lines, shown as `AI: V-006 100%` in Training, one click to prefill — but never decides pass/fail. Pitch as rule-driven scorer + lightweight supervised ML (TF-IDF + KNN) for unseen-syntax suggestion, human-approved — not LLM semantics.** AI also comes in as Gemini 2.5 Flash-Lite to turn those numbers into prose; every number the LLM writes is validated against the scorer's exact set, and if it hallucinates a number the report falls back to a template and is labeled `TEMPLATE-GENERATED`. The evidence itself lives in a hash-chained `normalized_results` array (`SHA-256(previous + canonical(entry))` with genesis seed, atomically locked via in-process `ReentrantLock` plus cross-process `FileChannel.lock`), so tampering is detectable and the report's `Chain Status: INTACT` can be verified with `verifyChain()`."
