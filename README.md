# Trinetra

## 1. What this is, in one paragraph

**For the judge who has 30 seconds:** Trinetra is a tool that lets a network team check whether their routers and switches are set up securely — even when those devices come from different vendors and speak different configuration languages — by uploading the devices' text config files, automatically comparing them against four major security standards, flagging anything it doesn't understand so a human can teach it once, and then producing a tamper-proof report that tells you what passed, what failed, how bad each failure is, and exactly what to type to fix it.

**One-sentence version to repeat:** *"Trinetra is an AI-assisted, multi-vendor network config auditor that turns uploaded CLI configs into standards-mapped, tamper-evident compliance reports without needing to re-deploy code when a new vendor is added."*

---

## 2. The problem, explained simply

Today, checking whether a network is configured securely means a human reading hundreds of lines of cryptic, vendor-specific text — Cisco IOS looks nothing like Juniper JUNOS, and each version adds its own quirks — then manually matching each setting against long checklists from CIS, NIST, ISO, and STIG, one device at a time. That work is slow, error-prone, and locked to the few people who know each vendor's syntax; add a new vendor and you usually have to rewrite tooling. The result is inconsistent audits, missed misconfigurations, and reports that can't prove they weren't tampered with after the fact. Trinetra was built to make that process repeatable, vendor-agnostic, and auditable.

---

## 3. How it works, step by step

*No code, just the flow a stakeholder can follow:*

1. **Upload a config** — You pick a session name and drag in one config file or many at once (for example, `cisco-lab-01.txt` and `juniper-lab-01.txt`). You can also add the device's serial number, hardware model, and OS version if you have them; if you leave OS blank, the system reads it from the config header itself. **Config-file upload is the PS-recommended primary method.**

2. **Fetch from IP/URL (optional, additive)** — Alternatively, supply an IP/hostname (SSH) or URL (HTTP GET) and credentials; the system fetches the raw config text and feeds it into the *exact same* ingestion pipeline as a file upload — no second parsing path. This is an auto-sourced convenience (requires network reachability), not a replacement for offline upload, and not a live-scanning/fingerprinting system.

3. **System reads it** — The system figures out which vendor it is, breaks the config into lines, and checks each line against what it already knows.

4. **Compare against security frameworks** — For every recognized setting, it decides pass/fail using the same rule a human auditor would apply, then maps that result to the controls in the frameworks you selected — CIS, NIST 800-53, ISO 27001, and STIG. You can choose to score all four or just the ones you care about.

5. **Flag what it doesn't know** — Any line it has never seen before is listed as "unrecognized," grouped by device.

6. **A human teaches it** — In a simple form, you tell it what that new line means: which vendor it belongs to, what security category it is, which standard it maps to, and how to fix it if it's wrong. You can also note which OS version you saw it on.

7. **It remembers** — That teaching is saved as a pattern. The next time you upload the same kind of config, the line is recognized automatically — no code change, no redeploy.

8. **Produce a report with fixes** — For any failures, it shows a risk level (critical/high/medium/low) and a numbered, device-specific list of commands to type to fix it. The whole thing is packaged into a report where every result is hash-chained, so anyone can verify afterward that the evidence hasn't been altered. Fetch-sourced devices appear identically but tagged `ingestion_method: live_fetch` for honest reporting.

## 5. What makes this different (differentiators)

### 5.1 Tamper-evident hash chain

*Plain language:* Every test result is linked to the one before it like a chain — if someone later edits or deletes a result, the chain breaks and the report says so. That lets an auditor prove the evidence hasn't been tampered with after collection.

*Technical detail:* `src/TrinetraSession.java:400-620` maintains `normalized_results[]` where each entry stores `chain_hash = SHA-256(previous_chain_hash + canonical_json(entry_without_hash))`, seeded with `GENESIS_HASH = SHA-256("TRINETRA_GENESIS")`. `previous_chain_hash` is tracked separately and updated atomically inside `withSessionStateLock` (in-process `ReentrantLock` + cross-process `FileChannel.lock` on `<file>.lock` sidecar, `TrinetraSession.java:320-383`) so concurrent uploads don't fork the chain. `verifyChain()` recomputes each link; `TrinetraAuditReportBuilder.java:290` and PDF metadata embed `Chain Status: INTACT (N links)` or `BROKEN at index`. The same chain is mirrored in the append-only SQLite `trinetra_audit.db` (`TrinetraAudit.java:110`) via per-run `run_uuid`, linking audit rows to chain tip.

### 5.2 Deterministic scorer with AI narration

*Plain language:* The compliance percentage is calculated by plain arithmetic from a file that lists which test maps to which control — no AI involved, so the number is always reproducible. AI is only used afterward to turn those numbers into readable paragraphs, and even then the system checks that the AI didn't invent any numbers.

*Technical detail:* `src/TrinetraComplianceScorer.java:41` is pure data transformation: for each `normalized_results` entry, `TrinetraCompliance.getControlMappings(testId)` (`src/TrinetraCompliance.java:64`) yields `framework → [controlIds]`; an accumulator per framework counts `tests_passed/tests_failed/controls_covered`; `compliance_percentage = round(tests_passed*100/total)`. No LLM call. `src/TrinetraNarrativeGenerator.java:41` then calls Gemini CLI (`TrinetraCommon.execGemini`, Gemini 2.5 Flash-Lite) with `renderAllowedValues` and `collectExpectedNumbers`; `validateNarrative()` extracts every numeric token and requires it to be in the scorer's exact set and that every framework's percentage appears — otherwise it retries once then falls back to `buildTemplateBody()` and the report is labeled `TEMPLATE-GENERATED`. The narrative never writes to the chain.

### 5.3 No-redeploy training loop

*Plain language:* When the system sees a command it doesn't recognize, it shows it to you, you fill in what it means, and from then on it recognizes that pattern on any device — you never edit code or restart the system.

*Technical detail:* `src/VendorTrainingMap.java:20` stores `vendor + pattern (regex) + securityCategory + controlMapping + remediation + osVersion` in `config/vendor_training_map.json`. `TrinetraConfigIngestor.java:131-150` classifies each config line: first `findMatch(canonicalVendor, line)` (regex `Pattern.compile` + substring fallback) against training entries, then `KNOWN_PATTERNS` (Cisco/Juniper/Generic), otherwise mark `unrecognized`. Training entries are written by `bridge/app.py:681` `POST /train` via atomic `NamedTemporaryFile` + `os.replace`; `VendorTrainingMap.load()` checks `Files.getLastModifiedTime` to invalidate its `cache` without process restart (`VendorTrainingMap.java:38-49`). `TrinetraSession.setUnrecognizedLines()` and `GET /unrecognized` surface per-device unrecognized lines to `frontend/src/pages/TrainingView.jsx:48` for the click-to-select form.

## 7. Known limitations, stated honestly

*Read this before talking to a judge — it prevents overclaiming.*

* **OS-version parsing is metadata-only.** The system detects `IOS XE 17.6.5`, `NX-OS 9.3(9)`, `JUNOS 20.4R3` from the config header and stores it as a distinct `os_version` field in `device_details`, and that field appears in every report. But the core parser does **not** branch its logic on OS version — a rule that is wrong on IOS but correct on IOS-XE will still be evaluated the same way. Full OS-version-aware normalization (Cisco IOS vs IOS-XE vs NX-OS producing different verdicts for the same V-code) was explicitly out of scope this prompt and remains open. *Pitch guidance:* say "OS-version awareness is at the metadata and reporting level today; parsing discrimination is on the roadmap," not "we fully handle every OS variant."

> **Do not claim STIG/OS-version/dataset-validation coverage beyond what Part A's scorecard actually shows.** Specifically: do not say "STIG fully covered for every V-code" (it's 14/15, V-106 cloud S3 has no NDM control — say "14 of 15 mapped, V-106 gap honestly in coverage_gaps"); do not say "remediation is auto-generated" (say "15/15 V-codes have curated numbered steps, new V-codes fall back to AI-suggested until curated"); do not say "OS-version parsing is fully branch-aware" (say "metadata-level awareness today, parsing discrimination on the roadmap"); do not say "tested against NCIIPC dataset" (say "self-constructed realistic configs, validated for submission, open to official sample validation"). A judge catching a false claim is worse than an honestly disclosed gap.

### Elevator pitch (30 seconds, judge walks by)

> "Network teams manage Cisco, Juniper, and other devices, each with its own cryptic config language, and they have to check every setting against CIS, NIST, ISO, and STIG — today that's manual. Trinetra lets them upload those config files — one or many at once — scores them against the four standards they choose, flags any line it doesn't recognize, lets them teach it what that line means without touching code, and then gives back a tamper-proof PDF that says what passed, what failed, how bad it is, and exactly what to type to fix it."

### Technical deep-dive answer (when a judge asks "how does the AI/training loop actually work?")

> "The compliance percentage is not from AI — it's deterministic: each test maps to controls in a JSON manifest, so `tests_passed/total` per framework is pure arithmetic. Training is pattern-based: you map an unrecognized line to a regex and a security category, it's stored in `vendor_training_map.json` and the ingestor's `findMatch` uses `Pattern.compile` against each line on the next upload — no Java redeploy, just an mtime cache check. AI comes in only as Gemini 2.5 Flash-Lite to turn those numbers into prose; every number the LLM writes is validated against the scorer's exact set, and if it hallucinates a number the report falls back to a template and is labeled `TEMPLATE-GENERATED`. The evidence itself lives in a hash-chained `normalized_results` array (`SHA-256(previous + canonical(entry))` with genesis seed, atomically locked via in-process `ReentrantLock` plus cross-process `FileChannel.lock`), so tampering is detectable and the report's `Chain Status: INTACT` can be verified with `verifyChain()`."

## Usage

```bash
trinetra -new <session> <target>          # create a new session
trinetra -sessions                        # list all sessions
trinetra -stat run <V-XXX> <session> <target>   # run one V-code check
trinetra -stat run-all <session> <target>       # run all stat tests
trinetra -stat status <session>                 # pass/fail tally
trinetra -mind -read <session> "query"     # query audit memory
trinetra -mind -suggest <session> "query"  # next V-code suggestion
trinetra -compliance-score <session> [--frameworks CIS,STIG]  # deterministic score, optionally filtered
trinetra -compliance-report <session> [--frameworks CIS]      # scorer + validated narrative
trinetra -audit-report <session> [--frameworks CIS,ISO27001]  # final deliverable
trinetra -doctor                           # system diagnostics
```

Bridge API (React or curl): `POST /api/session`, `POST /api/session/<name>/upload-config` (multipart `config` + `serial_number`/`hardware_model`/`os_version` or JSON `config_content`), `POST /api/session/<name>/fetch-config` (`source_type: ip|url`, `target`, `device_id`, `vendor`, optional `serial_number`/`hardware_model`/`os_version`, plus `username`/`password`/`ssh_key` for ip or `auth_token`/`auth_header` for url — thin fetch → same `TrinetraConfigIngestor.ingest(..., live_fetch)`), `GET /api/session/<name>/devices` (shows `ingestion_method: live_fetch` vs `config_upload`), `GET /api/session/<name>/score?frameworks=CIS,STIG`, `POST /api/session/<name>/train`, `GET /api/session/<name>/audit-report/pdf?frameworks=CIS` (landscape PDF, includes live-fetch devices).

## One-command backend startup (Linux / WSL)

From the repository root, run `make start` (or `python3 start_backend.py`).
The launcher creates an isolated `.venv`, installs pinned backend dependencies on
the first run or when requirements change, compiles Java, and starts the API at
`http://127.0.0.1:5000`. Stop it with Ctrl+C. First-time setup needs internet.

Prerequisites: Python 3.10+, its venv module, a JDK compatible with the Java
engine (Java 21 is tested), and Make. On Ubuntu, install these once with
`sudo apt install python3 python3-venv default-jdk make`.

The React frontend still starts separately with `cd frontend && npm run dev`.
This is a local development launcher, not a production deployment server.
Optional C++ network-probing tools are not started by the configuration-upload
API launcher. Existing sessions and configuration are left intact.
